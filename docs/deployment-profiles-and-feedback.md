# 部署版本、图片与反馈渠道

本文定义 Baihepailei 的两种公开展示模式，以及静态包、可部署包各自能承接的反馈能力。

## 推荐结论

正式在线站默认使用 `text`：不显示作品封面、证据截图和图文提示图片；站内反馈只接收文字、规则代码与来源链接。这样能显著减少页面请求、图片存储和出口流量。

通过网盘或 Hugging Face 分发的完整包可使用 `enhanced`：保留并显示索引中已有的图片元数据。是否能“上传反馈图片”取决于分发物是否带可写后端；纯静态文件本身无法接收上传。

## 三种可组合方案

| 方案 | 浏览图片 | 反馈入口 | 图片反馈 | 适用场景 |
| --- | --- | --- | --- | --- |
| 低流量正式站 | 不显示 | 注册用户站内表单 + 邮件 | 只提交图片链接 | 长期在线、控制带宽 |
| 增强静态包 | 显示随包图片 | 邮件 / 外部表单 / 公开问题单 | 由外部表单接收 | 网盘、Hugging Face 静态分发 |
| 增强可部署包 | 显示 | 站内表单 + 外部表单 | 外部表单，或部署者另接对象存储 | 自建完整服务 |

### 为什么静态包不能自己接收上传

静态站只有 HTML、CSS、JavaScript 和数据文件，没有数据库、鉴权会话或写入 API。它可以显示打包好的图片，但反馈必须送往邮件、Google Forms / Tally 等外部表单、GitHub Issues，或另一个可写服务。

## 环境变量

```env
# 正式低流量版（默认）
NEXT_PUBLIC_MEDIA_MODE=text

# 增强媒体版
# NEXT_PUBLIC_MEDIA_MODE=enhanced

# 可选反馈渠道；留空即不显示
NEXT_PUBLIC_FEEDBACK_EMAIL=feedback@example.com
NEXT_PUBLIC_FEEDBACK_FORM_URL=https://example.com/your-form
NEXT_PUBLIC_FEEDBACK_ISSUE_URL=https://github.com/example/repo/issues/new
```

`NEXT_PUBLIC_MEDIA_MODE=text` 只影响公开渲染，不删除数据库或索引里的封面 URL 元数据。因此同一份数据可以用于低流量正式站，也可以在增强分发版重新构建后显示图片。

## 渠道取舍

邮件最容易启用，适合少量文字、来源链接和继续沟通；缺点是整理、去重和状态跟踪较弱，也容易收到垃圾邮件。

外部表单最适合增强静态包。它可以设置必填字段、文件大小、文件数量、验证码和自动写入表格；缺点是依赖第三方服务及其存储政策。建议只允许 JPG、PNG、WebP，单文件不超过 5 MB，最多 4 张，并要求提交者写明章节、路线和来源。

公开问题单适合失效链接、错别字、页面显示错误等可公开问题。涉及剧透、个人信息或未公开材料时应改用站内表单或邮件。

完整自建上传需要鉴权、限流、病毒/格式检查、对象存储、生命周期清理和审核隔离。当前版本不把图片直接写入 `FeedbackSubmissions`，避免正式站被迫承担这组存储与滥用风险；需要图片时优先使用配置好的外部表单。

## 数据边界

- 用户提交不会自动更改 Works 的分级或发布状态。
- 25,048 条 `radar-research-records` 是内部研究档案，不等于正式评级。
- 后台审核工作台只允许逐条确认或标记争议，并记录审核人、时间与说明。
- “增强媒体”只改变公开展示，不改变证据状态、人工确认状态或页面提示。
