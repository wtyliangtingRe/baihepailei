# 公开投稿双入口决策记录（2026-09-05）

## 状态

**已采纳，作为后续公开投稿架构方向。**

本记录固定产品与安全边界，不表示相关 Cloudflare 服务或公开投稿仓库已经上线，也不创建待办事项。现行私有源码仓库和研究数据仓库继续保持私有。

## 决策

面向公众开放反馈时采用两个并行入口：

1. **普通访客**：匿名、纯文字、无附件的 Cloudflare 表单。
2. **熟悉 GitHub 的贡献者**：独立公开投稿仓库的 GitHub Issue Form。

不为了资料补充与纠错恢复本站邮箱密码注册。若将来账号体系具有投稿历史、修改本人待审稿、消息中心或贡献者信誉等独立产品价值，再另行决策；账号不能替代限流、反自动化和成本上限。

## 不变边界

- AWS 主站继续是只读公开快照，不增加匿名写入 API。
- 两条投稿渠道都只接收待核实线索，不自动修改正式 Works、Research、Assessment、Publication 或 Rating。
- 投稿系统与核心数据在运行时隔离；匿名入口不得拥有核心数据库地址、网络通路或凭据。
- 审核通过的数据只能由受信任的维护流程单向提升，优先形成可审阅的补丁或 PR。
- 当前两个私有仓库不会因为开放投稿而改为公开。
- 不把匿名表单伪装成“前端直连数据库”，也不把核心数据库拆一张公开表后称为隔离。

## 渠道一：匿名 Cloudflare 表单

### 接收范围

- 作品资料补充与纠错；
- 推荐收录新作品；
- 固定字段的纯文字说明；
- 数量和长度受限的公开来源 URL；
- 可选联系信息，但提交时不自动发送回执。

### 明确禁止

- 文件、图片、压缩包或其他附件；
- 预签名文件上传入口；
- 富文本 HTML；
- 在同步提交路径抓取链接、生成预览、运行 AI 分析或执行文档处理；
- 直接写核心数据库、正式研究记录、评级或发布状态。

### 最低安全与成本控制

- 投稿请求在 Cloudflare 边缘终止，不回源 AWS 处理；
- 先做方法、Content-Type、请求体大小和廉价频率检查，再做 Turnstile 服务端验证；
- 边缘与应用层双重限流，并结合 IP/网段、签名 Cookie、内容哈希和重复抑制；
- 对字段采用 allowlist、类型和长度上限，安全转义所有待审显示内容；
- 设置全局每日写入硬上限，达到上限或依赖异常时 fail closed；
- 使用独立、最小权限的待审存储和凭据，设置自动过期与容量边界；
- 提供无需重新部署主站即可关闭入口的 kill switch；
- 对明显拒绝流量采用小响应和有限、可采样日志，避免日志成为新的费用来源。

此渠道的成本原则是：攻击者最多造成匿名投稿暂时不可用，不能让请求继续消耗 AWS 主站、核心数据库或无上限的外部服务费用。

## 渠道二：独立公开 GitHub 投稿仓库

- 新建独立的公开 issues-only 仓库，不复用或公开 `baihepailei`、`baihepailei-research-data`。
- 仓库只包含投稿说明、行为规范、标签和兼容的 `work-correction.yml`、`new-work.yml` Issue Forms。
- 不包含应用源码、研究数据、内部证据、个人信息、密钥、自动导入凭据或核心数据库连接信息。
- Issue 内容一律视为不可信待审输入；关闭、标记或讨论 Issue 不会自动改变正式数据。
- 网站通过 `NEXT_PUBLIC_FEEDBACK_ISSUE_URL` 指向该仓库；默认私有仓库入口在切换前继续仅供协作者使用。
- 来源链接优先于附件。即使附件由 GitHub 托管，维护者也应按不可信文件处理，本站不得自动下载或镜像到 AWS。

## 审核与单向提升

无论来自哪个入口，统一经过：

```text
untrusted submission
→ isolated pending item
→ identity / source / spoiler review
→ accepted or rejected
→ reviewed patch / PR
→ versioned public snapshot
```

`accepted` 表示允许进入受信任维护流程，不表示用户输入可以原样落入正式字段。任何评级、警示、身份合并或新 Work 创建仍遵循现有研究与审核规则。
